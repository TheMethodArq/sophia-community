# Sophia v2 — Testing Strategy

## Overview

Testing in Sophia v2 operates at two levels:
1. **Testing Sophia itself** — ensuring the platform works correctly
2. **Testing apps built by Sophia** — ensuring output quality meets enterprise standards

This document covers both.

---

## Part 1: Testing Sophia (The Platform)

### Unit Tests

**Framework:** Vitest (carried forward from v1)

**Coverage Targets:**
- Core modules: 90%+ (orchestrator, governance, policy engine, approval router)
- Adapters/integrations: 80%+ (can mock external systems)
- CLI commands: 70%+ (thin wrappers around core)
- Dashboard: 70%+ (component testing)

**Key Test Areas:**

| Module | What to Test |
|--------|-------------|
| Orchestrator | Task routing, state management, checkpoint save/restore, context bundle preparation |
| Governance Engine | Gate evaluation, policy checks, approval classification |
| Approval Router | Classification logic (auto/inform/human), escalation format |
| Token Tracker | Budget enforcement, model routing, cost calculation |
| Context Manager | File summary generation, context compression, bundle assembly |
| Agent Adapters | Context translation, result parsing, error handling |
| Sprint Planner | Task decomposition, dependency detection, budget estimation |
| Memory System | Pattern storage/retrieval, cross-project queries, decay |

**Test Naming Convention:**
```typescript
describe('ApprovalRouter', () => {
  it('auto-approves file creation within declared stack', () => {});
  it('requires human approval for undeclared dependencies', () => {});
  it('escalates security-sensitive changes regardless of stack', () => {});
});
```

### Integration Tests

**Framework:** Vitest with test fixtures

**What They Cover:**
- Full gate evaluation cycles (entry criteria → evaluation → exit artifacts)
- Sprint execution simulation (plan → task sequence → sprint completion)
- Agent adapter round-trips (prepare context → mock execution → harvest result)
- Integration adapter connections (mock Leantime API, mock git operations)

**Test Fixtures:**

### E2E Tests (Sophia Platform)

**Framework:** Playwright (for dashboard) + custom CLI test harness

**What They Cover:**
- Full workflow: scaffold → plan → build → test → deliver (with mocked agents)
- Dashboard interactions: view projects, approve plans, resolve escalations
- CLI commands: all commands with expected inputs produce expected outputs
- Recovery: crash during build → resume from checkpoint

**E2E Test Strategy:**
- Use mock agent adapters that return pre-defined results (no actual LLM calls)
- This makes E2E tests fast, deterministic, and free (no token cost)
- Real agent integration tested separately in a dedicated integration test suite

## Part 2: Testing Apps Built by Sophia

This is the testing strategy that Sophia's agents follow when building user apps.

### TDD Workflow

Every coding task follows Test-Driven Development:

```
1. Tester Agent generates failing test from task spec
2. Builder Agent implements code to pass the test
3. Builder Agent refactors if needed
4. All tests verified passing before commit
```

### Test Pyramid

```
          ┌──────┐
          │ E2E  │  Few, expensive, persona-journey based
         ┌┴──────┴┐
         │ Integ. │  Moderate, API/component interaction
        ┌┴────────┴┐
        │   Unit   │  Many, fast, isolated
        └──────────┘
```

### Unit Tests (Per Task)

**Generated by:** Tester Agent (Sonnet)

**Input:** Task specification + function signatures

**Rules:**
- Every public function/method has at least one test
- Test the behavior, not the implementation
- Cover: happy path, edge cases, error cases
- No mocking of the thing being tested (only mock dependencies)
- Tests must be deterministic (no time-dependent, random, or network-dependent tests)

**Example Generated Test:**
```typescript
// tests/unit/services/task-service.test.ts
import { describe, it, expect, vi } from 'vitest';
import { TaskService } from '@/services/task-service';
import { createMockDb } from '../helpers/mock-db';

describe('TaskService.createTask', () => {
  it('creates a task with valid input', async () => {
    const db = createMockDb();
    const service = new TaskService(db);
    const task = await service.createTask({
      title: 'Test task',
      assignee: 'user-1',
      dueDate: new Date('2024-02-01'),
    });

    expect(task.id).toBeDefined();
    expect(task.title).toBe('Test task');
    expect(task.status).toBe('todo');
  });

  it('throws on empty title', async () => {
    const db = createMockDb();
    const service = new TaskService(db);

    await expect(
      service.createTask({ title: '', assignee: 'user-1' })
    ).rejects.toThrow('Task title is required');
  });

  it('throws on invalid assignee', async () => {
    const db = createMockDb();
    db.users.findById = vi.fn().mockResolvedValue(null);
    const service = new TaskService(db);

    await expect(
      service.createTask({ title: 'Test', assignee: 'nonexistent' })
    ).rejects.toThrow('Assignee not found');
  });
});
```

### Integration Tests (Per Sprint)

**Generated by:** Tester Agent at sprint boundary

**What They Cover:**
- API endpoint round-trips (request → handler → service → db → response)
- Component rendering with data (fetching → loading → display)
- Multi-service interactions (e.g., creating a task sends a notification)
- Database migrations apply cleanly

**Run At:** Sprint completion gate

### E2E Tests (Final Acceptance)

**Framework:** Playwright

**What They Cover:** Complete user persona journeys as defined in requirements.

**Generation Process:**
1. Planner creates E2E test plan from persona journeys during planning phase
2. Tester Agent generates Playwright test scripts during final acceptance phase
3. Each persona's complete journey is a separate test suite
4. All GUI interactions are tested: navigation, forms, buttons, modals, toasts

**Example E2E Test Plan Entry:**
```yaml
persona: Team Member
journey: Sign up and create first task
steps:
  - Navigate to /signup
  - Fill registration form (name, email, password)
  - Submit form
  - Verify redirect to /dashboard
  - Click "New Task" button
  - Fill task form (title, description, due date)
  - Submit task
  - Verify task appears in task list
  - Verify task status is "To Do"
assertions:
  - Registration creates user in database
  - Dashboard shows welcome message with user's name
  - Task list updates without page refresh
  - Task has correct default status
```

**Recording:**
```typescript
// e2e/journeys/team-member-create-task.spec.ts
import { test, expect } from '@playwright/test';

test.describe('Team Member: Sign up and create first task', () => {
  test.use({
    video: 'on',              // Record video
    screenshot: 'on',         // Capture screenshots on failure
    trace: 'on',              // Capture trace for debugging
  });

  test('completes full journey', async ({ page }) => {
    // Journey steps...
  });
});
```

**Recording & Hashing:**
- All E2E test runs produce video recordings (Playwright built-in)
- Recordings stored in `tests/e2e/recordings/`
- Each recording is SHA-256 hashed
- Hash stored in audit trail for verification
- Recordings classified as internal (not committed to public repo)

### Quality Gate Tests (Final Acceptance)

These are not functional tests but quality assertions:

**Lighthouse Audit:**
```bash
# Run by Sophia's test pipeline
npx lighthouse http://localhost:3000 \
  --output=json \
  --output-path=tests/reports/lighthouse.json \
  --chrome-flags="--headless"

# Assertions (enforced by policy)
# Performance >= 90
# Accessibility >= 90
# Best Practices >= 90
# SEO >= 90
```

**Accessibility Audit:**
```typescript
// e2e/quality/accessibility.spec.ts
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test.describe('Accessibility', () => {
  const pages = ['/', '/dashboard', '/tasks', '/settings'];

  for (const path of pages) {
    test(`${path} passes WCAG AA`, async ({ page }) => {
      await page.goto(path);
      const results = await new AxeBuilder({ page })
        .withTags(['wcag2a', 'wcag2aa'])
        .analyze();
      expect(results.violations).toHaveLength(0);
    });
  }
});
```

**Security Scan:**
- Dependency audit: `npm audit` (zero high/critical vulnerabilities)
- Secret detection: scan all files for API keys, tokens, passwords
- OWASP check: validate input sanitization, CSRF protection, secure headers

## Test Execution Schedule

| Checkpoint | Tests Run | Blocking? |
|-----------|-----------|-----------|
| Per task commit | Unit tests for modified files | Yes — task fails if tests fail |
| Sprint completion | All unit tests + integration tests | Yes — gate blocks |
| Final acceptance | Unit + integration + E2E + Lighthouse + a11y + security | Yes — gate blocks |
| CI/CD (every push) | Lint + typecheck + unit tests + build | Yes — PR blocks |
| CI/CD (sprint tag) | All of the above + integration | Yes — release blocks |

## Test Infrastructure

### Test Database
- SQLite in-memory for unit tests (fast, isolated)
- SQLite file-based for integration tests (persists across test steps)
- Same ORM/migration tooling as production (Prisma test mode)

### Test Data
- Factory functions for generating test entities (not raw fixtures)
- Deterministic IDs for snapshot testing
- No shared state between tests

### CI Pipeline Test Stage
```yaml
# Generated in .github/workflows/ci.yaml
test:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-node@v4
    - run: npm ci
    - run: npm run test:unit -- --coverage
    - run: npm run test:integration
    - uses: actions/upload-artifact@v4
      with:
        name: coverage-report
        path: coverage/
```

## Failure Handling

### Unit Test Failure During Build
1. Builder agent receives failing test output
2. Agent attempts fix (up to 2 retries with error context)
3. If still failing after retries, escalate to user with:
   - Test code
   - Implementation code
   - Error output
   - What was tried

### Integration Test Failure at Sprint Gate
1. Tester agent analyzes failure
2. If isolated to one component: attempt targeted fix
3. If cross-cutting: escalate with impact analysis
4. Sprint gate remains blocked until resolved

### E2E Test Failure at Final Acceptance
1. Categorize failure: visual (screenshot diff), functional (assertion), accessibility (a11y violation)
2. Visual failures: may indicate design system drift — attempt component-level fix
3. Functional failures: likely implementation bug — trace to source, fix, re-run
4. Accessibility failures: usually missing attributes — auto-fixable in most cases
5. Any unresolved failure blocks acceptance and escalates to user
